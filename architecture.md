# Architecture

## Назначение документа

Документ описывает архитектурные решения проекта PricePulse.

Цель документа:
* зафиксировать структуру системы;
* объяснить принятые решения;
* снизить количество повторных обсуждений;
* упростить дальнейшее развитие проекта.

---

# Обзор системы

PricePulse — сервис мониторинга цен на маркетплейсах с уведомлениями через Telegram.

Пользователь добавляет ссылку на товар через Telegram бота.

Система:
1. Сохраняет подписку и **мгновенно** запускает первичную проверку.
2. Периодически проверяет цену с помощью **умного планирования (eta)**, где каждая успешная проверка планирует следующую через заданный интервал (`PRICE_CHECK_INTERVAL`).
3. Сохраняет историю изменений.
4. **Кэширует данные** (список подписок, агрегированная история цен, сгенерированные графики) для снижения нагрузки на БД и ускорения ответов.
5. **Отправляет уведомления при достижении целевой цены (target_price)** с умной логикой:
   - Настраиваемый пользователем период cooldown (от 1 до 168 часов).
   - Автоматический сброс флага уведомления при росте цены выше целевой.
6. **Визуализирует историю цен** через генерацию графиков (Matplotlib) с поддержкой разных периодов (7д, 30д, всё время) и отображением линии целевой цены.
7. **Автоматически очищает** старую историю цен для архивных подписок, предотвращая неограниченный рост БД.

# Основные компоненты

## FastAPI

Ответственность:
* Полноценный REST API для всех операций с данными.
* Валидация данных через Pydantic.
* Управление подписками, пользователями, историей цен.
* **Кэширование ответов API** делегировано в `Service Layer` (например, `PriceService` управляет кэшем истории цен), роутеры остаются "тонкими".
* Структурированное логирование HTTP запросов через middleware.

FastAPI предоставляет канонический HTTP-интерфейс к системе. Telegram Bot взаимодействует с ним через HTTP-запросы, используя единый `Service Layer` на стороне API, что гарантирует отсутствие дублирования бизнес-логики (DRY).

---

## PostgreSQL

Источник истины (Source of Truth).

Хранит:
* пользователей
* подписки (включая `last_check_at`, `last_success_at`, `target_price`, `alert_sent`, `last_alert_at`, `cooldown_hours`, `consecutive_errors`, `status`)
* историю цен
* ошибки парсинга

Никакие бизнес-данные не должны существовать только в Redis.

---

## Redis

Используется как вспомогательное хранилище для кэширования и ускорения ответов.

Назначение:
* **API кэширование**: списки подписок, агрегированная история цен.
* **Кэширование последних цен** (TTL синхронизирован с `PRICE_CHECK_INTERVAL`).
* **Кэширование графиков**: Base64-строки внутри JSON-объектов (TTL 5 мин).

Redis может быть очищен без потери данных (данные восстановятся из PostgreSQL или будут обновлены при следующем парсинге).

### Структура кэша
```text
subs:user:{user_id}                # Список подписок пользователя (JSON, TTL 30s)
prices:history:{sub_id}:{period}   # Агрегированная история цен (JSON, TTL = интервал проверки)
price:latest:{subscription_id}     # Последняя цена (строка, TTL = интервал проверки)
chart:{subscription_id}:{period}   # Сгенерированный график (Base64 JSON, TTL 5m)
```

## RabbitMQ

Основной брокер сообщений.

Используется для:
* надежной доставки фоновых задач парсинга
* гарантии доставки (persistence, acks)
* обработки отказов через **Dead Letter Exchange (DLX)** для задач, исчерпавших попытки retry.

## Celery Worker & Smart Scheduling

### Умное планирование (Smart Scheduling via `eta`)
Вместо периодического опроса БД через Celery Beat ("тупой метроном"), используется умное планирование. После успешного выполнения (или логической ошибки) задачи `parse_price`, она сама планирует свое следующее выполнение:
```python
next_check_at = datetime.now(timezone.utc) + timedelta(seconds=settings.price_check_interval)
parse_price.apply_async(args=[subscription_id], eta=next_check_at)
```
Это устраняет нагрузку на БД и гарантирует точный интервал проверок без дрейфа таймера. При старте системы скрипт `app/workers/resync_queue.py` инициализирует эти циклы для всех активных подписок.

### ProcessBrowser (singleton per process)
Воркер использует **Playwright** (headless Chromium) для парсинга маркетплейсов.
* **ProcessBrowser singleton:** Каждый Celery worker-процесс имеет свой экземпляр браузера, который переиспользуется между задачами для экономии времени запуска (2-5 сек) и памяти.
* **Очистка ресурсов:** `worker_max_tasks_per_child=1` гарантирует перезапуск процесса воркера после каждой задачи, предотвращая утечки памяти Chromium.

### Производительность и Retry
* Парсинг занимает **2-4 секунды** благодаря отказу от BeautifulSoup в пользу регулярных выражений и прямому извлечению JSON.
* Задачи имеют явные retry политики (`max_retries=3`, `retry_backoff=True`) для обработки временных сетевых сбоев. Ошибки парсинга (логические, например `ParserError`) не ретраятся, а инкрементируют счетчик ошибок.
* **Rate limiting на уровне Celery не применяется**, так как это провоцирует капчу Ozon. Используются естественные задержки (`_human_delay`).

### Фоновая очистка (Cleanup Task)
Саморегистрирующаяся задача `cleanup_old_price_history` запускается при старте системы и планирует себя каждые 24 часа. Она удаляет записи `PriceHistory` старше 90 дней только для подписок со статусом `ARCHIVED`.

## Telegram Bot

Основной интерфейс пользователя.

Бот реализует **единый виджет UX** — все взаимодействия происходят в одном редактируемом сообщении, без спама новыми сообщениями в чате.

### Inline Keyboard Navigation
Вместо текстовых команд используется интерактивная навигация через inline keyboard (пагинация, установка цены, удаление, графики).

### Graceful Error Handling
При ошибках Telegram API (устаревший callback, сетевые сбои прокси) бот не ломает виджет, а показывает пользователю понятную "всплывашку" (`show_alert=True`), сохраняя последнее успешное состояние интерфейса и предлагая кнопки для повторной попытки.

### Cloudflare Worker прокси
Для обхода блокировок Telegram API в РФ используется Cloudflare Worker, который проксирует запросы к `api.telegram.org`.

---

## NotificationService

Сервис умных уведомлений о достижении целевой цены.
* **Buffer (5%):** Автоматический сброс `alert_sent` когда цена поднимается выше `target_price * 1.05`.
* **Cooldown:** Минимальный период между повторными уведомлениями (настраивается пользователем, по умолчанию 24 часа).

---

## PriceChartService

Сервис генерации и кэширования графиков изменения цен.
1. **Генерация в памяти:** Использует `matplotlib` в отдельном потоке (`asyncio.to_thread`), чтобы не блокировать event loop.
2. **Downsampling на стороне БД:** Вместо выгрузки всех записей, используется агрегация через `DATE_TRUNC` (часы для 7 дней, дни для 30 дней, месяцы для "всё время"). Это гарантирует, что объем передаваемых данных никогда не превысит 100-200 строк, исключая риски OOM.
3. **Base64-кэширование в Redis:** Бинарные данные PNG сохраняются как Base64-строка внутри JSON-объекта для совместимости с `decode_responses=True`.
4. **Делегирование отправки фото на API:** Из-за ограничений Cloudflare Worker прокси при обработке `multipart/form-data`, бот вызывает `POST /api/v1/subscriptions/{id}/chart/send`, и FastAPI самостоятельно отправляет фото через "чистый" `httpx.AsyncClient`.

## Извлечение данных (Оптимизация Sprint 3A)

Ozon использует React Server Components. Вместо тяжёлого парсинга всего DOM через BeautifulSoup, `OzonParser` теперь использует:
1. Регулярные выражения для поиска `<script type="application/ld+json">` (название товара).
2. Регулярные выражения для поиска атрибутов `data-state` и извлечения из них JSON через `html.unescape()`.
3. **Fallback-механизмы:** Если основная структура не найдена, парсер ищет цену в `<meta property="product:price:amount">` или в JSON-LD `offers.price`, а имя товара в `<title>`.

# Слои приложения

```text
Telegram Bot / FastAPI (Parallel Consumers)
 ↓
Service Layer (Business Logic, Cache Invalidation, Orchestration)
 ↓
Repository Layer (Data Access, joinedload for N+1 prevention)
 ↓
Database (PostgreSQL) / Redis
```

* **Service Layer:** Отвечает за бизнес-логику. Является единым источником истины для действий, инициируемых как из Bot, так и из API. Инкапсулирует логику кэширования.
* **Repository Layer:** Отвечает за доступ к данным. Следует принципу "один запрос вместо двух" и использует `joinedload`/`selectinload` для предотвращения проблемы N+1 при загрузке связанных сущностей.

# Асинхронность и обработка ошибок

Проект использует async-first подход. Celery задачи синхронные (prefork), но внутри используют `asyncio.run()` для вызова асинхронных сервисов. Для избежания конфликтов event loop воркер создаёт собственный async engine через `create_worker_engine()`.

### Retry Strategy
Celery задачи автоматически ретраятся при сетевых ошибках: `max_retries=3`, `retry_backoff=True` (экспоненциальная задержка до 10 минут). Логические ошибки парсера (`ParserError`) не ретраятся, а инкрементируют `consecutive_errors`. После 3 неудачных попыток задача отправляется в Dead Letter Queue (DLQ).

# Логирование

Используется `structlog` с человекочитаемым форматом (ConsoleRenderer) и Rich Traceback для отладки.

**Оптимизация логов:**
* Технические шаги запуска Playwright переведены на уровень `DEBUG`.
* Добавлены чёткие маркеры `parse_price_started` и `parse_price_completed` (с указанием цены и `duration_ms`).
* Ошибка логируется один раз на верхнем уровне задачи (Single Traceback).
* Добавлен `CeleryTaskNoiseFilter` для подавления стандартных сообщений Celery (`received`, `succeeded`), что критически важно при умном планировании.

# Принятые архитектурные решения (ADR)

## ADR-001
**Решение:** Использовать RabbitMQ вместо Redis как основной брокер сообщений.
**Причина:** RabbitMQ обеспечивает более надежную доставку сообщений и лучше подходит для дальнейшего масштабирования.
**Статус:** Accepted

## ADR-002
**Решение:** Использовать SQLAlchemy 2.0 Async.
**Причина:** Единый современный ORM стек для FastAPI.
**Статус:** Accepted

## ADR-003
**Решение:** Использовать Telegram Bot как основной интерфейс пользователя.
**Причина:** Минимальные затраты на frontend на раннем этапе проекта.
**Статус:** Accepted

## ADR-004
**Решение:** Использовать Celery с RabbitMQ для фоновых задач.
**Причина:** Надежная доставка задач, встроенная поддержка ретраев, возможность горизонтального масштабирования.
**Статус:** Accepted

## ADR-005
**Решение:** Извлекать данные Ozon из атрибутов `data-state` вместо `__NEXT_DATA__`.
**Причина:** Ozon перешел на React Server Components. Атрибуты `data-state` содержат состояние React-компонентов и стабильнее.
**Статус:** Accepted

## ADR-006
**Решение:** Использовать Playwright (headless Chromium) вместо HTTP-клиентов для парсинга Ozon.
**Причина:** Ozon использует продвинутую защиту от ботов, блокирующую обычные HTTP-запросы (403 Forbidden). Playwright запускает реальный браузер.
**Статус:** Accepted

## ADR-007
**Решение:** Использовать раздельные поля `last_check_at` и `last_success_at`.
**Причина:** Пользователю важно видеть, когда система пыталась проверить цену, и когда это удалось.
**Статус:** Accepted

## ADR-008
**Решение:** Сделать интервал проверки цен конфигурируемым через `PRICE_CHECK_INTERVAL`.
**Причина:** Разные сценарии использования требуют разных интервалов (от 60 сек для тестов до 3600 сек для продакшена).
**Статус:** Accepted

## ADR-009 (Deprecated)
**Решение:** ~~Запускать парсинг только через Celery Beat, без вызова `parse_price.delay()` при создании подписки.~~
**Причина изменения:** Архитектура с Celery Beat ("тупой метроном") была признана анти-паттерном, создающим излишнюю нагрузку на БД.
**Статус:** Deprecated (Заменено на ADR-044)

## ADR-010
**Решение:** Использовать Docker Compose profiles для опциональных сервисов.
**Причина:** Позволяет запускать систему без бота (CLI режим) для разработки или с ботом (`--profile bot`) для продакшена.
**Статус:** Accepted

## ADR-011
**Решение:** Использовать RequestLoggingMiddleware вместо стандартного uvicorn access log.
**Причина:** Структурированное логирование через structlog и единый формат для всего приложения.
**Статус:** Accepted

## ADR-012
**Решение:** Использовать ProcessBrowser singleton per process.
**Причина:** Явное управление жизненным циклом браузера, каждый worker-процесс имеет свой экземпляр.
**Статус:** Accepted

## ADR-013
**Решение:** Вынести фабрики engine/session в `app/workers/database.py`.
**Причина:** Устранение дублирования кода и централизация конфигурации для Celery задач.
**Статус:** Accepted

## ADR-014
**Решение:** Использовать PriceCache для инкапсуляции sync/async Redis логики.
**Причина:** Единый интерфейс `set()` и `get()` без дублирования проверок типа клиента.
**Статус:** Accepted

## ADR-015
**Решение:** Использовать singleton-паттерн для Redis соединений.
**Причина:** Переиспользование соединений и устранение накладных расходов на их создание.
**Статус:** Accepted

## ADR-016
**Решение:** Использовать Rich traceback с ограничением locals и single traceback pattern.
**Причина:** Предотвращение вывода огромных HTML-страниц и дублирования ошибок в логах.
**Статус:** Accepted

## ADR-017
**Решение:** Использовать `@lru_cache` вместо глобальных переменных для singleton database engine в FastAPI.
**Причина:** Автоматический singleton, потокобезопасность и ленивая инициализация без глобального состояния.
**Статус:** Accepted

## ADR-018
**Решение:** Обновлять `last_check_at` только для успешно созданных задач.
**Причина:** Гарантия атомарности: время обновляется только для подписок, для которых действительно созданы задачи в очереди.
**Статус:** Accepted

## ADR-019
**Решение:** Использовать Cloudflare Worker как прокси для доступа к Telegram API.
**Причина:** Обход блокировок Telegram API в РФ без необходимости настройки VPN на сервере.
**Статус:** Accepted

## ADR-020
**Решение:** Использовать единый виджет UX (редактирование сообщений).
**Причина:** Чистый чат без спама, пользователь не теряет контекст при навигации.
**Статус:** Accepted

## ADR-021
**Решение:** Реализовать graceful error handling для ошибок Telegram API.
**Причина:** Виджет не ломается при временных проблемах, пользователь видит понятные сообщения об ошибках.
**Статус:** Accepted

## ADR-022
**Решение:** Реализовать умную логику уведомлений с buffer (5%) и cooldown.
**Причина:** Предотвращение спама уведомлениями при колебаниях цены вокруг target_price.
**Статус:** Accepted

## ADR-023
**Решение:** Использовать ConversationHandler для интерактивных диалогов в Telegram Bot.
**Причина:** Интуитивный UX, чёткое управление состоянием диалога и возможность отмены.
**Статус:** Accepted

## ADR-024
**Решение:** Внедрить Redis кэширование с автоматической инвалидацией, инкапсулированной в Service Layer.
**Причина:** Снижение нагрузки на PostgreSQL. Логика кэширования и инвалидации строго инкапсулирована в сервисах (например, `PriceService`), роутеры не управляют кэшем напрямую.
**Статус:** Accepted

## ADR-025
**Решение:** Оптимизировать парсинг Ozon, отказавшись от BeautifulSoup в пользу регулярных выражений.
**Причина:** Ускорение парсинга с ~40 секунд до 2-4 секунд.
**Статус:** Accepted

## ADR-026
**Решение:** Использовать упрощенную стратегию защиты от блокировок (естественные задержки), отказавшись от сложных stealth-плагинов.
**Причина:** Агрессивные stealth-техники сами по себе являются сильными сигналами для антибот-систем Ozon.
**Статус:** Accepted

## ADR-027
**Решение:** Устранить дрейф таймера путем фильтрации избыточных логов состояний Celery и точного расчета интервалов.
**Причина:** Обеспечение нулевого накапливающегося дрейфа и чистых логов.
**Статус:** Accepted

## ADR-028
**Решение:** Реализовать настраиваемый пользователем период cooldown для уведомлений (от 1 до 168 часов).
**Причина:** Гибкость для разных сценариев использования (распродажи vs долгосрочный мониторинг).
**Статус:** Accepted

## ADR-029
**Решение:** Делегировать отправку фотографий графиков (`sendPhoto`) на сторону FastAPI.
**Причина:** Cloudflare Worker прокси некорректно обрабатывал потоковую загрузку `multipart/form-data` из `python-telegram-bot`.
**Статус:** Accepted

## ADR-030
**Решение:** Объединить активные и архивные подписки в едином меню "Графики цен".
**Причина:** Пользователь может захотеть посмотреть историю цен архивированного товара.
**Статус:** Accepted

## ADR-031
**Решение:** Внедрить паттерн Graceful Error Handling с кнопками действий.
**Причина:** Предотвращение UX-тупиков при сетевых сбоях.
**Статус:** Accepted

## ADR-032
**Решение:** Использование составного индекса `(is_active, status, last_check_at)` в таблице `subscriptions`.
**Причина:** Оптимизация главного запроса воркера для выборки задач без Full Table Scan.
**Статус:** Accepted

## ADR-033
**Решение:** Строгая нормализация и отказ от избыточных полей.
**Причина:** Предотвращение дублирования смысла данных.
**Статус:** Accepted

## ADR-034
**Решение:** Downsampling истории цен на стороне БД через `DATE_TRUNC`.
**Причина:** Защита от OOM. Данные агрегируются с шагом, зависящим от периода, гарантируя передачу не более 100-200 строк.
**Статус:** Accepted

## ADR-035
**Решение:** Хранение бинарных данных (графиков) в Redis через сериализацию Base64-строки в JSON-объект.
**Причина:** Совместимость с глобальной настройкой `decode_responses=True` Redis-клиента.
**Статус:** Accepted

## ADR-036
**Решение:** Кэширование агрегированной истории цен в Redis с TTL, синхронизированным с `PRICE_CHECK_INTERVAL`.
**Причина:** Обеспечивает консистентность данных и предотвращает устаревание кэша.
**Статус:** Accepted

## ADR-037
**Решение:** Использование RabbitMQ в качестве брокера сообщений для Celery.
**Причина:** Надежная доставка задач и гарантии при падении воркеров.
**Статус:** Accepted

## ADR-038
**Решение:** Использование RabbitMQ на полную мощность.
**Причина:** Реализована настройка Dead Letter Exchanges (DLX) для failed tasks, что позволяет не терять задачи, исчерпавшие попытки retry, и анализировать их вручную.
**Статус:** Accepted

## ADR-039
**Решение:** Централизация конфигурации Celery.
**Причина:** Единообразие и упрощение масштабирования через `app/workers/celery_app.py`.
**Статус:** Accepted

## ADR-040
**Решение:** Использование Celery с prefork и `worker_max_tasks_per_child=1` для задач с Playwright.
**Причина:** Предотвращение накопления утечек памяти Chromium.
**Статус:** Accepted

## ADR-041
**Решение:** Использование ProcessBrowser singleton.
**Причина:** Переиспользование headless Chromium между задачами в рамках одного процесса экономит время и память.
**Статус:** Accepted

## ADR-042
**Решение:** Явные retry политики для задач парсинга.
**Причина:** `max_retries=3` и `retry_backoff=True` для сетевых сбоев. Логические ошибки парсера не ретраятся.
**Статус:** Accepted

## ADR-043
**Решение:** Отказ от Celery `rate_limit` для задач парсинга Ozon.
**Причина:** Rate limiting провоцирует капчу. Используются естественные задержки (`_human_delay`).
**Статус:** Accepted

## ADR-044
**Решение:** Переход на умное планирование через `eta` вместо периодического опроса БД через Celery Beat.
**Причина:** Устранение нагрузки на БД и дрейфа таймера. Задачи планируются с точным временем выполнения после каждой проверки. Первичный запуск происходит мгновенно при создании/реактивации подписки.
**Статус:** Accepted

## ADR-045
**Решение:** Естественные задержки (`_human_delay`) работают лучше, чем агрессивные stealth-плагины.
**Причина:** Stealth-плагины провоцируют детектирование антибот-системами.
**Статус:** Accepted

## ADR-046
**Решение:** Использование FastAPI с трехслойной архитектурой (Router → Service → Repository).
**Причина:** Тестируемость, масштабируемость и интеграция с asyncpg/Redis.
**Статус:** Accepted

## ADR-047
**Решение:** Dependency Injection через `Depends()`.
**Причина:** Упрощение тестирования (mocking) и единая точка конфигурации.
**Статус:** Accepted

## ADR-048
**Решение:** Централизация общей логики в Service Layer.
**Причина:** Избежание дублирования кода и обеспечение консистентности поведения системы независимо от точки входа (API или Bot).
**Статус:** Accepted

## ADR-049
**Решение:** Кэширование на уровне API через Redis.
**Причина:** Снижение нагрузки на БД для часто запрашиваемых данных (TTL 30-60 секунд).
**Статус:** Accepted

## ADR-050
**Решение:** Сохранение полноценного REST API (API-First подход) при использовании единого Service Layer.
**Причина:** FastAPI предоставляет канонический HTTP-интерфейс. Bot и внешние клиенты используют единую бизнес-логику, сохраняя API рабочим и протестированным.
**Статус:** Accepted

## ADR-051
**Решение:** Внедрение саморегистрирующейся фоновой задачи `cleanup_old_price_history` для очистки старых данных.
**Причина:** Контролируемый рост таблицы `price_history`. Задача удаляет записи старше 90 дней только для подписок со статусом `ARCHIVED` и планирует свой следующий запуск через 24 часа, не используя Celery Beat.
**Статус:** Accepted

### ADR-052: Управление очередью и предотвращение дубликатов (Текущее и будущее состояние)

**Текущее решение (Sprint 4):** 
При старте системы скрипт `resync_queue` выполняет `celery_app.control.purge()` для полной очистки очереди RabbitMQ, а затем перестраивает её заново на основе состояния PostgreSQL (`last_check_at`). Задачи сортируются по времени последней проверки (asc, nullsfirst), чтобы обеспечить приоритетное обновление "просроченных" подписок. Это гарантирует отсутствие дубликатов (Task Storm) и простоту поддержки.

**Планируемое улучшение (Future):** 
Рассмотреть внедрение идемпотентности задач на уровне Redis (например, паттерн `celery-once` или кастомная distributed lock с TTL, строго синхронизированным с `eta`). Это позволит избежать полной очистки очереди (`purge`) при горизонтальном масштабировании воркеров (когда несколько инстансов воркеров запускаются параллельно), но требует тщательной отладки взаимодействия TTL блокировки и времени `eta`, чтобы избежать deadlocks.

## ADR-053
**Решение:** Оркестрация отправки уведомлений о снижении цены вынесена из `PriceParsingService` в задачу воркера `parse_price.py`.
**Причина:** В предыдущей архитектуре `PriceParsingService` мутировал состояние подписки (`alert_sent = True`) до того, как воркер мог отправить уведомление. Это приводило к молчаливому пропуску отправки и потере `old_price` (отображалось как `N/A`). Перенос оркестрации в воркер гарантирует, что `old_price` считывается до начала парсинга, а уведомление формируется с корректными данными и единообразной логикой.
**Статус:** Accepted

## ADR-054
**Решение:** Внедрен Fallback к истории цен при формировании уведомлений. Если поле `current_price` в таблице `subscriptions` равно `NULL`, система выполняет один быстрый запрос к `price_history` для получения последней известной цены.
**Причина:** Защита от edge-кейсов (сбои транзакций, гонки состояний), когда основная таблица временно не содержит актуальной цены, но история сохранена. Это гарантирует отсутствие `N/A` в уведомлениях без избыточной нагрузки на БД (запрос по индексу с `LIMIT 1`).
**Статус:** Accepted

## ADR-055
**Решение:** Предотвращение Task Storm через отказ от Celery `autoretry`. Из декоратора задачи `parse_price` удалены параметры `autoretry_for`, а из блока `except` удален `raise`. Обработка ошибок и планирование следующего запуска полностью делегированы механизму `eta` внутри самой задачи.
**Причина:** Сочетание встроенного `autoretry` Celery и ручного планирования через `eta` при ошибках приводило к экспоненциальному дублированию задач в очереди RabbitMQ. Единый источник планирования (`eta`) гарантирует ровно одну задачу на интервал, даже при сбоях.
**Статус:** Accepted

# Архитектурные принципы

При проектировании компонентов соблюдаются следующие принципы.

## Single Responsibility
Каждый сервис отвечает только за одну область ответственности (FastAPI — HTTP, Worker — фон, Parser — данные, Bot — UX).

## Weak Coupling
Компоненты взаимодействуют через четкие интерфейсы. Bot и FastAPI являются параллельными потребителями единого Service Layer.

## Failure Isolation
Отказ одного компонента не приводит к остановке всей системы. Остановка Bot не влияет на парсинг; временные проблемы с прокси не ломают виджет бота; исчерпание retry отправляет задачу в DLQ, а не роняет воркер.

## Source of Truth
PostgreSQL является единственным источником истины. Redis используется только как эфемерный кэш.

## Stateless Services
Все сервисы проектируются максимально stateless. После перезапуска любой сервис полностью восстанавливает работу, используя PostgreSQL, RabbitMQ и скрипт инициализации очередей (`resync_queue.py`).

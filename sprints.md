**Обработка ошибок:**
- `ParserError`, `ValueError` → не ретраим (ошибки парсинга)
- `ConnectionError`, `TimeoutError` → ретраим через Celery autoretry
- `SoftTimeLimitExceeded` → помечаем как failed без retry

```python
# Было: 2 запроса
subscription = await repo.get(subscription_id)  # SELECT
if subscription.user_id != user_id: return False
await repo.delete(subscription)  # DELETE

# Стало: 1 запрос
deleted = await repo.delete_by_user(subscription_id, user_id)  # DELETE с WHERE
```

**Атомарность check_all_subscriptions:**
```python
# Было: обновление сразу после создания задачи
for subscription in subscriptions:
    parse_price.delay(subscription.id)
    await repo.mark_last_check_now(subscription.id)  # Если delay() упадёт — уже обновлено

# Стало: обновление только успешных задач
successful_ids = []
for subscription in subscriptions:
    parse_price.delay(subscription.id)
    successful_ids.append(subscription.id)

for sub_id in successful_ids:
    await repo.mark_last_check_now(sub_id)
```

## Задача 22. Rate Limiting и защита от блокировок

Статус: ⚠️ Осознанно упрощена

### Описание

Попытка внедрить сложные механизмы защиты от блокировок Ozon (stealth-плагины, глобальный rate limiter через Redis, retry с exponential backoff) привела к обратному эффекту — Ozon начал чаще показывать капчу.

### Попытки (откачены)
* [ ] `playwright-stealth` плагины — провоцировали детектирование
* [ ] Глобальный rate limiter через Redis — не решал проблему fingerprint
* [ ] Блокировка ресурсов через `page.route()` — ломала рендеринг
* [ ] Рандомизация User-Agent — не влияла на антибот

### Оставлено (работает стабильно)
* [x] Естественные `_human_delay` (0.2-1.5 сек) для имитации человеческого поведения
* [x] `--disable-blink-features=AutomationControlled` в Chromium
* [x] `Object.defineProperty(navigator, 'webdriver', {get: () => undefined})`
* [x] Встроенный Celery `autoretry` для сетевых ошибок

### Вывод

Для headless Chromium без прокси **естественные задержки работают лучше**, чем агрессивные stealth-плагины. Полноценная защита от блокировок требует **пула резидентных/мобильных прокси**, что является инфраструктурной задачей, а не задачей кода парсера.

### Рекомендация на будущее

При росте числа подписок до 100+ и появлении массовых блокировок:
1. Подключить пул резидентных прокси через существующий `ProxyService`
2. Настроить ротацию прокси на уровне `MarketplaceHttpClient`
3. Не возвращаться к stealth-плагинам — они только усугубляют проблему

## Задача 29. Синхронизация API и Bot (DRY принцип)

Статус: 🚧 В работе

### Описание
FastAPI остается полноценным слоем приложения. Чтобы избежать дублирования бизнес-логики, и Telegram Bot, и FastAPI должны использовать единый `Service Layer` (`app/services/*.py`).

### Подзадачи
- [ ] Проверить, что все действия бота (создание, удаление, обновление подписки) делегируются в `Service Layer`, а не дублируют логику репозиториев.
- [ ] Проверить, что API-роутеры (`app/api/routers/`) используют те же самые методы `Service Layer`.
- [ ] Убедиться, что кэширование (`CacheService`) и инвалидация кэша работают одинаково корректно при вызове и из API, и из Bot.
- [ ] Сохранить все публичные API-эндпоинты (`/api/v1/subscriptions`, `/api/v1/users`) полностью рабочими и покрытыми Pydantic-схемами.

### ADR
- **ADR-051**: Проект следует API-First подходу. FastAPI предоставляет полноценный REST интерфейс для всех операций. Telegram Bot и внешние клиенты используют единую бизнес-логику через `Service Layer`, что гарантирует консистентность данных и отсутствие дублирования кода (DRY).

### Результат

- Отсутствие дублирования бизнес-логики между Bot и API.

## Задача 30. Downsampling истории цен (DATE_TRUNC)

Статус: 🚧 В работе

### Описание

Защита от OOM и деградации производительности при росте истории цен. Вместо `SELECT *` без ограничений используется агрегация на стороне БД с шагом, зависящим от запрошенного периода.

### Подзадачи

- [ ] Реализовать `get_aggregated_price_history()` в `PriceHistoryRepository`
- [ ] Логика шага агрегации:
  - 24 часа → сырые данные (или `LIMIT 100`)
  - 7 дней → группировка по часам (`DATE_TRUNC('hour', ...)`)
  - 30 дней → группировка по дням (`DATE_TRUNC('day', ...)`)
  - Всё время → группировка по месяцам (`DATE_TRUNC('month', ...)`)
- [ ] Возвращать `avg`, `min`, `max` для каждого bucket'а
- [ ] Обновить `PriceChartService` для использования агрегированных данных
- [ ] Обновить API endpoint `GET /prices` для передачи параметра `days`
- [ ] Добавить unit-тесты для разных периодов

### ADR

- **ADR-034**: Для построения графиков изменения цен используется стратегия **Downsampling на стороне БД** через `DATE_TRUNC` с шагом, зависящим от запрошенного диапазона. Это гарантирует, что объем передаваемых данных никогда не превысит 100-200 строк, исключая риски OOM и деградации отклика.

### Результат

- Защита от OOM при росте истории цен (35 000+ записей за год)
- Ускорение построения графиков в 10-50 раз
- Читаемые графики (сглаженный тренд вместо шума)

## Задача 33. Retry политики для задач парсинга

Статус: 🚧 В работе

### Описание

Задачи парсинга не имеют явных retry политик. При временных сбоях (сеть, блокировки Ozon) задача падает без повторной попытки.

### Подзадачи

- [ ] Добавить retry политики в `parse_price.py`:
  ```python
  @app.task(
      bind=True,
      max_retries=3,
      default_retry_delay=60,
      retry_backoff=True,
      retry_backoff_max=600,
  )
  def parse_price(self, subscription_id: int):
      try:
          # ... логика парсинга
      except Exception as exc:
          raise self.retry(exc=exc)
  ```
- [ ] Разделить исключения:
  - `ParserError`, `ValueError` → не ретраим (ошибки парсинга)
  - `ConnectionError`, `TimeoutError` → ретраим через Celery retry
  - `SoftTimeLimitExceeded` → помечаем как failed без retry
- [ ] Добавить логирование retry попыток
- [ ] Добавить метрики (количество retry, причины падений)

### ADR

- **ADR-042**: Задачи парсинга имеют явные retry политики (`max_retries=3`, `retry_backoff=True`) для обработки временных сбоев (сеть, блокировки Ozon). Ошибки парсинга (`ParserError`, `ValueError`) не ретраятся.

### Результат

- Устойчивость к временным сбоям
- Меньше пропущенных проверок из-за сетевых ошибок
- Прозрачность (логирование retry попыток)

## Задача 34. Dead Letter Exchange (DLX) в RabbitMQ

Статус: 🚧 В работе


### Результат

- Возможность ручного разбора и повторной обработки
